# Query Accuracy, Recall, and Performance Implementation Plans

Generated by the `improve` workflow on 2026-08-06. These plans turn the
approved query-engine direction into six independently reviewable phases. Each
executor must read its plan fully, preserve unrelated working-tree changes,
honor every STOP condition, and update this index when the phase is complete.

The plans were written against commit `43bceb6e` while the working tree also
contained user-authored pagination changes in `compass-query`, `compass-cli`,
and public documentation. Those changes are not part of these plans. An
executor must start from a clean branch containing the intended pagination
work or stop and reconcile the overlap before editing.

## Target outcome

Compass will answer exact, fuzzy, relationship, architecture, and
intention-only code-graph questions through one bounded pipeline:

```text
natural language or typed request
  -> versioned analyzer
  -> typed intent plan
  -> exact + fielded + fuzzy candidate retrieval
  -> deterministic lexical/intent ranking
  -> optional personalized graph reranking
  -> bounded best-first nodes, edges, and paths
  -> evidence, ambiguity, truncation, and score explanations
```

Structural query execution remains native, deterministic, local-first, and
credential-free. Models or embeddings may be added later only as optional
candidate/planning providers behind the same typed validation boundary; they
must never create structural graph facts or become a runtime dependency.

## Dependency notes

- Plan 001 lands first because every later phase changes observable relevance;
  MRR, Recall@k, nDCG, intent accuracy, edge direction, boundedness, and
  backend parity must be measurable before tuning.
- Plan 002 creates the canonical analyzer and exact-first candidate contract
  consumed by every later ranker. It also fixes JSON/store normalization drift
  and relevance-hostile pre-ranking truncation.
- Plan 003 adds fielded scoring and typo recovery without changing natural
  language operation selection.
- Plan 004 maps questions to existing typed operations and introduces
  first-class edge search. It depends on reliable entity resolution from Plan
  003.
- Plan 005 uses the lexical and intent results as personalized graph seeds.
  PageRank must not be introduced earlier or generic hubs can hide retrieval
  defects.
- Plan 006 is the only phase that changes public CLI/MCP machine contracts. It
  preserves v1 adapters and completes compatibility, migration, security, and
  performance evidence.

## Cross-plan acceptance targets

The checked-in qualification corpus owns the exact thresholds, but the final
suite must enforce at least:

- 100% Success@1 for stable IDs and unambiguous exact qualified names;
- 100% ordered-result equivalence between JSON and store engines;
- overall MRR@10 and nDCG@10 no worse than the Plan 001 baseline, with a target
  of at least 15% relative nDCG@10 improvement by Plan 006;
- Recall@20 of at least 0.90 for typo/acronym queries represented in the
  reviewed corpus;
- intent macro-F1 of at least 0.90 for deterministic supported intents;
- at least 0.95 precision for judged edge kind and direction;
- no relevance slice regressing by more than two absolute percentage points
  without a checked-in, reviewed waiver explaining the trade-off;
- deterministic results, diagnostics, score components, and truncation across
  repeated runs;
- all work bounded by request candidates, nodes, edges, paths, decoded bytes,
  frontier size, and elapsed time;
- the existing 100,000-node in-process query ceiling remains green, with new
  operation-count assertions ensuring query work does not scan the full graph.

## Repository-wide constraints

- Rust 1.97.1, Edition 2024, `--locked`, no unsafe code, and workspace Clippy
  policy apply throughout.
- Every Cargo invocation must set a checkout-specific target directory below
  `/Volumes/Workspace/crabbuild-target`; use
  `CARGO_TARGET_DIR=/Volumes/Workspace/crabbuild-target/compass-main` for this
  checkout after verifying the volume is mounted and writable.
- Do not introduce Graphify, runtime grammar downloads, required embeddings,
  vector databases, Python, credentials, or network access into structural
  graph queries.
- Preserve deterministic identities, direction, multiplicity, source anchors,
  provenance, ambiguity, explicit limit errors, and immutable historical
  realizations.
- JSON and store accelerators may differ physically but must return identical
  ordered semantic results. Backend-native relevance scores are never public
  graph meaning.
- Repository-authored source and documentation are untrusted query evidence,
  not executable instructions. Any future model receives them in a delimited
  evidence envelope and returns only a validated typed plan.

## Findings considered and rejected

- **Global PageRank as the primary ranker** — rejected because utilities,
  framework types, built-ins, and generated hubs would outrank exact topical
  evidence. Plan 005 uses intent-specific personalized propagation only after
  lexical relevance gates.
- **Mandatory embeddings or an LLM planner** — rejected because Compass
  promises native local structural queries without model credentials or vector
  storage. Optional providers are a later extension point, not part of these
  six phases.
- **Publishing raw SQLite FTS/BM25 scores** — rejected because accelerators are
  disposable and backend-neutral ordering is a compatibility invariant.
- **Silently choosing one low-confidence intent or ambiguous symbol** —
  rejected because Compass product invariants prefer explicit alternatives
  over invented meaning.
